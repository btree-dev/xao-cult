# Events & Ticketing

**Scope:** event pages, on-chain ticket purchase/tier setup, and QR-based door authentication. Excludes contract negotiation/minting itself (see `contracts-nft.md`) and Waku messaging (see `xaomsg-messaging.md`).

## Purpose

An "event" is really a deployed `ShowContract` (see `contracts-nft.md`) — event metadata (name, venue, date, flyer) lives on-chain on that contract, not in a database. Each `ShowContract` has an associated `XAOTicket` collection contract that mints ERC-721 tickets in tiers (Comp/Presale/GA/VIP/Custom), sold for USDC. QR-based authentication exists so door staff can scan a ticket's on-chain address+tokenId and call `scanTicket` to mark it redeemed, without needing the buyer's wallet present.

## Key modules

- `src/lib/web3/eventcontract.ts` — 3.7k-line file, almost entirely ABI constants: `SHOW_CONTRACT_FACTORY_ABI`, `SHOW_CONTRACT_ABI` (aliased as `EVENT_CONTRACT_ABI`), `XAO_TICKET_ABI`. Not prose-readable; grep it for function signatures.
- `src/hooks/useAddTicketType.ts` — `useAddTicketType` is a **dead stub** (logs and returns `undefined`, tier creation deliberately skipped at contract-creation time because `XAOTicket` isn't deployed until both parties sign). The real tier-creation hook is `useAddTierToXAOTicket` in the same file, called later from the contract detail page.
- `src/hooks/useBuyTickets.ts` — `useBuyTickets`: ERC20 `approve` (if price > 0) → `XAOTicket.buyTicket(tierId)`. `useTicketCollection`: reads `ShowContract.ticketCollection()` to get the `XAOTicket` address.
- `src/pages/event/[id].tsx` — event detail page, reads **entirely from-chain** via `useReadContracts` against a `ShowContract` address. Does not use `src/backend/eventsdata.ts`.
- `src/pages/event/[id]/purchase.tsx`, `confirm.tsx`, `ticket-confirmation.tsx` — purchase wizard → confirm → receipt/localStorage-write.
- `src/pages/stats/tickets/index.tsx` — "My Tickets" list (redeemed/unredeemed tabs).
- `src/pages/stats/tickets/[id].tsx` — ticket detail page; resolves either from on-chain reads or localStorage depending on ID format (see Data model below).
- `src/pages/TicketAuthenticate/TicketQR.tsx` — 3-tab shell: Scan / Authenticate (disabled) / Me.
- `src/pages/TicketAuthenticate/TicketScan.tsx` — camera-based QR scan + on-chain redemption call. This is the real door-scanner logic.
- `src/pages/TicketAuthenticate/TicketAuthentication.tsx`, `Access.tsx` — result/status screens after a scan.
- `src/backend/eventsdata.ts` — `EventDocs`: static mock array, largely vestigial (see Gotchas).
- `src/backend/ticket-services/ticketdata.ts` — `mockTickets`, `TicketsQR`: static mock arrays still driving the "My Tickets" list UI.
- `src/backend/ticketAuthData.ts` — static fixture for the "Me" tab identity card.

## Data flow / lifecycle

**Setup (organizer):**
1. `ShowContract` deployed and both parties sign (see `contracts-nft.md`) → this triggers `XAOTicket` collection deployment.
2. Organizer adds ticket tiers via `useAddTierToXAOTicket().addTier(...)` → `XAOTicket.addTier(ticketType, customName, priceUSDC, quantity, onSaleTimestamp, party1ResaleBPS, party2ResaleBPS, resellerBPS)`.

**Purchase (buyer):**
3. `event/[id]/purchase.tsx` → `useBuyTickets().buyTickets(showContractAddress, ticketCollectionAddress, usdcAddress, tierId, priceUSDC)`: USDC `approve` (waits for confirmation) then `XAOTicket.buyTicket(tierId)`.
4. `confirm.tsx` → `ticket-confirmation.tsx`: on "See in Assets", writes a record into `localStorage['purchasedTickets']` with id `blockchain-{contractAddress}-{Date.now()}` (see Gotchas — this ID/ticketCode scheme does **not** match what the scanner expects).
5. "My Tickets" (`stats/tickets/index.tsx`) currently renders `TicketsQR` mock data, not this localStorage array or live chain state (see Gotchas).
6. Ticket detail (`stats/tickets/[id].tsx`) branches on the id prefix: `chain-`/`blockchain-` → tries on-chain reads first (`XAOTicket.showContract/tokenToTier/scanned/getTier` + `ShowContract.eventName/flyerDNSLink/venueName/eventStartDate`), falls back to the `purchasedTickets` localStorage entry if the chain read throws.
7. QR image itself is generated by handing `ticketCode` to a **third-party public API**: `https://api.qrserver.com/v1/create-qr-code/?size=200x200&data=<ticketCode>` (`stats/tickets/[id].tsx:167-168`) — no local QR-generation library is used despite `html5-qrcode` being a dependency (that package is scan-only).

**Door authentication (staff):**
8. `TicketScan.tsx` opens camera via `html5-qrcode`'s `Html5Qrcode.start(...)`, decodes the payload as `ticketCollectionAddress:tokenId` (`scannedData.split(':')`, requires `parts[0]` to start with `0x`).
9. On "Redeem": `readContract(XAOTicket.scanned(tokenId))` to reject already-redeemed tickets → reads `tokenToTier`/`getTier` for a display name → `writeContract(XAOTicket.scanTicket(tokenId), gas: 200_000)`, waits for receipt.
10. Routes to `/TicketAuthenticate/Access?status=...&reason=...` with one of: `invalid_format`, `wallet_not_connected`, `invalid_contract`, `already_redeemed`, `not_organizer` (caller lacks `SCANNER_ROLE`), `checkin_failed`, `unknown`, or `success`.
11. On-chain, `scanTicket` behaves differently before/after the event's `doorsTime`: pre-doors emits `TicketAuthenticated` (auth only), post-doors emits `TicketRedeemed` and sets `scanned = true` (per code comment at `TicketScan.tsx:156-158` — verify against `ContractNFT.sol`/ticket contract source, not re-derived here).

## Data model / key types

- **Ticket ID schemes in the wild (two, inconsistent):**
  - New/authoritative: `chain-{ticketCollectionAddress}-{tokenId}` — parsed by `stats/tickets/[id].tsx` `parseChainId()`, address is the first 42 chars after the prefix.
  - Legacy: `blockchain-{contractAddress}-{Date.now()}` written by `ticket-confirmation.tsx`, with `ticketCode: '{contractAddress}:{txHash || contractAddress}'` — this is a `ShowContract` address + tx hash/itself, **not** the `ticketCollection:tokenId` pair the scanner (`TicketScan.tsx`) expects. A ticket purchased through the current wizard and then scanned at the door will fail `invalid_contract`/format checks unless something downstream normalizes it — no such normalization was found in this pass.
- **QR payload = `ticketCode` = `"{ticketCollectionAddress}:{tokenId}"`**. Plaintext, unsigned — anyone who can read/photograph the code can reconstruct it; the only gate is the on-chain `SCANNER_ROLE` check on `scanTicket` (a screenshot lets someone *attempt* redemption, but only a `SCANNER_ROLE` wallet can succeed, and it's one-shot since `scanned` flips to true).
- **Ticket tiers** (`XAOTicket` enum): `0=Comp, 1=Presale, 2=General Admission, 3=VIP, 4=Custom` (`useAddTicketType.ts:42-48`, `TicketScan.tsx:148`).
- **`AddTicketTypeParams`** (`useAddTicketType.ts`): `ticketTypeName, onSaleDate: bigint, numberOfTickets: bigint, ticketPrice: bigint (USDC, 6 decimals), isFree`.
- Money: USDC throughout, 6 decimals; helpers `dollarToWei`/`weiToDollar`/`dateTimeToTimestamp` in `useAddTicketType.ts`.

## Integration points

- **contracts-nft**: `ShowContract` is the event; `XAOTicket` is a child collection deployed once both parties sign. Ticket purchase/scan hooks read `ShowContract.ticketCollection()` and `ShowContract.eventName/venueName/flyerDNSLink/eventStartDate` directly — no separate off-chain event record.
- **Supabase / backend-data**: none of this subsystem's live functionality touches Supabase — `eventsdata.ts` and `ticketdata.ts`/`ticketAuthData.ts` are local static TS files, not DB-backed. If a `supabase` events/tickets table exists, it is not wired to these pages as of this pass.
- **Web3/wallet**: `useWeb3()` gates scanning (must be connected to call `scanTicket`); `wagmi`'s `config` (from `src/wagmi.ts`) is used directly via `@wagmi/core`'s `readContract`/`writeContract` rather than the `useReadContract`/`useWriteContract` hooks in the scan flow specifically.

## Gotchas & constraints

1. **"My Tickets" list is fully mocked.** `stats/tickets/index.tsx` renders `TicketsQR` from `ticket-services/ticketdata.ts`, not the `purchasedTickets` localStorage array a real purchase writes to, and not any live chain query. A real purchase is invisible on the list page even though its detail page (`/stats/tickets/[id]`) can resolve correctly if you have the right URL/id.
2. **Two incompatible ticket-ID/QR-payload formats coexist** (see Data model). Anything built on top of this subsystem should standardize on `chain-{ticketCollectionAddress}-{tokenId}` / `{ticketCollectionAddress}:{tokenId}` and treat the `blockchain-*` legacy shape as needing migration or removal.
3. **The "Me" tab (personal QR) is a static demo, not real.** `TicketQR.tsx`'s "Me" tab renders a hardcoded SVG (`/Ticket-Auth_Icons/QR.svg`) plus fake identity fields from `ticketAuthData.ts` (`@xao_vortex33`, a fabricated wallet/DID). It is not wired to the current wallet or any actual owned ticket. The "Authenticate" tab button is `disabled` in JSX.
4. **`EventDocs` (`eventsdata.ts`) is near-vestigial** despite its comment block claiming "real-time protocols" / "polling" / "WebSocket" updates — none of that exists in this codebase. It's only imported once, in `contracts/create-contract-section.tsx`, to render a single promo title (`EventDocs[0].title`). The actual event browsing/detail experience is on-chain via `ShowContract` reads.
5. **QR generation depends on a third-party public API** (`api.qrserver.com`) with no fallback — if that service is down or blocked, ticket QR codes won't render. No local QR-generation library is installed; `html5-qrcode` (the only QR dep) only decodes.
6. **`useAddTicketType` looks callable but silently no-ops.** Don't wire new UI to it; use `useAddTierToXAOTicket` for real tier creation.
7. QR payload is unsigned plaintext — security relies entirely on the on-chain `SCANNER_ROLE` gate and one-shot `scanned` flag, not on the QR code itself.

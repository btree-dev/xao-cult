# XaoMsg Messaging (Waku)

**Scope:** client-only, wallet-to-wallet encrypted messaging over Waku — chat, contact-card exchange, and off-chain contract negotiation, with zero backend/server component. Historical design rationale and the decisions behind this shape live in `docs/superpowers/specs/2026-07-19-xaomsg-direct-dm-design.md`, `docs/superpowers/specs/2026-07-24-waku-login-unlock-sync-design.md`, and `docs/superpowers/specs/2026-07-27-event-thread-separation-design.md` (plus earlier `docs/superpowers/plans/2026-04-22-xaomsg-phase1-*.md` and `docs/superpowers/plans/2026-07-28-event-thread-separation-plan.md`) — this doc is **current-state only**; treat those specs as "why," not "what's true today" (see Spec drift below).

## Purpose

XaoMsg replaces a former XMTP-based chat stack (fully removed) with a Waku light-client transport carrying messages over **two independent kinds of encrypted thread per wallet pair**: a **DM thread** (cold-message by wallet address, no contract required — chat + contact-card profile sync) and, separately, one **event thread per contract draft** (compose/counter/approve a contract before and after it's minted on-chain). A DM thread and a draft's event thread between the same two wallets use different thread IDs, different topics, and different derived keys — negotiating one contract never exposes chat history from another draft or from the DM thread, and vice versa. Everything is end-to-end encrypted so only the two wallets can read it; Waku itself is a dumb relay with no server-side conversation list, so the client reconstructs all indexing itself from `localStorage` + Waku store replay.

## Key modules

Identity & crypto (`src/lib/xaomsg/`):
- `session.ts` — session keypair + `SessionCert` (wallet-signed authorization), 30-day `localStorage`-persisted session
- `crypto.ts` — AES-GCM encrypt/decrypt primitives + the legacy deterministic per-show-address thread key (still used for the legacy on-chain contract chat fallback, see Gotchas)
- `ecies.ts` — ECDH + HKDF key derivation: the deterministic DM conversation key (`deriveDmConversationKeyRaw`), the per-draft event conversation key (`deriveEventConversationKeyRaw`, domain-separated by `draftId` so every draft between the same two wallets gets an independent key), and the ECIES wrap/unwrap used for inbox notices
- `envelope.ts` — canonical JSON hashing, envelope build/sign/verify
- `conversationKey.ts` — `localStorage` cache of each thread's raw AES key (keyed `xao-cult-dm-convkeys-v2`, shared by DM and event threads — the cache key is the thread ID, which already disambiguates them)

Transport & addressing:
- `waku.ts` — lazy-singleton Waku light node (publish / subscribe / store-query history); `queryHistory`'s callback also receives each message's real Waku publish `timestamp`, used by `queryPeerKeyBundle` (see Gotchas)
- `threadId.ts` — `threadIdForShow(address)` (legacy, per-contract-address thread) and `threadIdForDraft(draftId)` (per-draft event thread, domain-separated from the former so a draftId can never collide with an address-shaped thread ID)
- `dmThreadId.ts` — DM thread ID derivation (per-address-pair, independent of any draft)
- `topicId.ts` / `inboxTopic.ts` — opaque Waku content-topic derivation from a thread ID / from an address

Discovery & indexing:
- `inbox.ts` — per-address inbox topic: public key-bundle publish, ECIES-encrypted `ThreadNotice` (kind `'dm' | 'event'`) publish/verify/decode, `queryPeerKeyBundle` (peer cert lookup), `eventBackfillDedupeKey`
- `conversationStore.ts` — `localStorage` DM conversation list (`xao-cult-dm-conversations`), owner-keyed, merge-by-latest-activity — **DM-only**; event/draft notices never populate this list (see Data flow)
- `offchainContracts.ts` — `localStorage` off-chain draft store (`xao-cult-offchain-contracts`): upsert/approve/mint/dedup, plus `resolveDraftForContract` (matches a minted on-chain contract back to the draft/thread it came from — see Off-chain contract drafts below)
- `sync.ts` — headless `syncAllKnownThreads()` (the post-unlock one-time login backfill, covering both DM peers and event/draft threads) and `backfillEventThreadFromNotice()` (the same event-thread backfill, reused live by `useXaoInbox`)
- `merge.ts` — dedupe+sort resolved messages by `messageId`/`sentAt`, shared by live/store/optimistic paths

Payload/content-type handling:
- `types.ts` — `ContentType` enum + all payload shapes (wire format)
- `contactCard.ts` — build/apply contact-card payload + "already sent" localStorage flag
- `draftSync.ts` — `applyDraftMessage`, routes a resolved PROPOSAL/COUNTER_PROPOSAL/ACCEPT/SYSTEM message into the draft store, cross-checked against the thread's own `expectedDraftId` (see Off-chain contract drafts); shared by live (`useXaoEvent`) and headless (`sync.ts`) paths. DM threads never call this.
- `messagePreview.ts` — per-content-type conversation-list preview text

Hooks (`src/hooks/`):
- `useXaoThread.ts` — the shared pipeline: subscribe → decrypt → verify → merge → post; every content type goes through `post()`
- `useXaoDm.ts` — wraps `useXaoThread` for a wallet-pair DM: derives thread ID + DM conversation key, auto-sends contact card once ready, routes inbound CONTACT_CARD to the profile cache. Deliberately never touches the off-chain draft store — contract negotiation content doesn't ride the DM thread.
- `useXaoEvent.ts` — wraps `useXaoThread` for one draft's own event thread: derives `threadIdForDraft(draftId)` + the per-draft event conversation key, routes inbound PROPOSAL/COUNTER_PROPOSAL/ACCEPT/SYSTEM into the draft store via `applyDraftMessage`, and exposes `notifyThread(contractAddress?)` — publishes a discovery/mint `ThreadNotice` to both the peer's inbox and the sender's own inbox, idempotent, safe to call on every proposal send and again at mint time
- `useResolveEventThread.ts` — given a minted contract's on-chain address + its real on-chain party1/party2, resolves which thread its chat should render on: the draft's own per-draft thread (`mode: 'draft'`) if a local draft is both minted-to that address AND has matching parties, else the legacy address-keyed thread (`mode: 'legacy'`)
- `useXaoMsg.ts` — wraps `useXaoThread` for the **legacy** deployed-contract chat path (`threadIdForShow`, deterministic thread key, no ECDH) — only reached when `useResolveEventThread` falls back (see Gotchas)
- `useXaoInbox.ts` — subscribes to own inbox topic (live) + replays its full history once per mount, publishes own key bundle, feeds the Search-page DM conversation list from `'dm'`-kind notices, and fire-and-forget backfills any `'event'`-kind notice via `sync.ts`'s `backfillEventThreadFromNotice` (so a counterparty already live in the app sees a new draft without reloading — see Data flow)
- `useXaoMsgSession.ts` — the `unlock()` React hook (mint keypair → wallet signature → persist session)

## Identity & encryption

- **Session keypair**: `session.ts` mints a fresh secp256k1 keypair per unlock; `SessionCert` binds `walletAddress ↔ sessionPublicKeyHex ↔ expiresAtUnixMs` via an EIP-191 wallet signature (`sessionChallengeString`, locked format, "do NOT change without a v2"). Every envelope carries the sender's cert, so verifying one message yields the sender's wallet-attested public key for free.
- **Duration & storage — current**: `SESSION_DURATION_MS = 30 * 24 * 60 * 60 * 1000` (30 days), persisted in `localStorage` under `xao-msg-session-<wallet lowercased>` (survives tab/browser close; only explicit logout or expiry clears it). Falls back to an in-memory `Map` if `localStorage` throws (some private-browsing modes) — session then only lasts the tab's lifetime.
- **DM conversation key** — deterministic ECDH, not transported. `ecies.deriveDmConversationKeyRaw(mySessionPriv, theirSessionPub)` does `ECDH → HKDF-SHA256(info="xao-dm-convkey-v1")` — both parties independently compute the *same* 32-byte AES key from nothing but each other's session pubkey (obtained via the peer's key-bundle on their inbox topic). No key generation, no wrapping, no "who generates it" race.
- **Event (per-draft) conversation key** — same ECDH shared secret as the pair's DM key, but domain-separated with `HKDF(info="xao-event-convkey-v1:" + draftId)` (`deriveEventConversationKeyRaw`). Every draft between the same two wallets gets an independent key; a leaked event key exposes only that one draft, never the pair's DM history or any other draft. Used unchanged both pre- and post-mint — minting never rotates the thread's key.
- **Inbox notices** use real ECIES: `ecies.wrapBytes`/`unwrapBytes` derive a separate KEK via `HKDF(info="xao-dm-kek-v1")` (domain-separated from both conv-key HKDFs) and AES-GCM-wrap the notice payload to the recipient's session pubkey. Both `'dm'`- and `'event'`-kind `ThreadNotice`s ride this same wrapping.
- **Legacy on-chain contract chat threads** (`threadIdForShow`) still use `crypto.deriveDeterministicThreadKey(showAddress)` — a plain `keccak256(domain ‖ address)`, no ECDH at all. See Gotchas: this is a known-weak Phase-1 leftover that DM and event threads upgraded past but the legacy fallback did not.

## Data flow / lifecycle

1. **Login → unlock.** `src/pages/index.tsx` redirects to `src/pages/unlock-chat.tsx` after Dynamic login completes. `/unlock-chat`: if an unexpired session exists, skip straight to `/dashboard`; otherwise auto-fire `unlock()` (gated on `isWalletReady`, not just `address` — wagmi's wallet client hydrates a render or two after `address` appears, and calling `unlock()` before it's ready silently no-ops).
2. **Unlock signs & persists.** `useXaoMsgSession.unlock()` mints a session keypair, builds+signs the challenge string, persists `{cert, privateKeyHex}` to `localStorage`.
3. **Background sync (fire-and-forget).** On session ready, `unlock-chat.tsx` calls `syncAllKnownThreads(address, session)` without awaiting, then immediately `router.replace('/dashboard')`. `sync.ts`: publishes own key bundle → replays own inbox-topic store history, splitting notices by `kind` into DM peers and event/draft entries → for every DM peer, derives (or reuses) the DM conversation key and replays that thread's history; for every event/draft entry, `backfillEventThreadFromNotice` records any mint-pairing claim (parties-checked, see Off-chain contract drafts) and replays that draft's own thread through `draftSync.applyDraftMessage` — so both the Chat conversation list and the Negotiation tab's off-chain drafts are current without visiting either page first.
4. **Live event-notice delivery.** `useXaoInbox` (mounted on the Search page) doesn't just replay history once — it also subscribes live and fire-and-forget backfills any `'event'`-kind notice it sees arrive, deduped per `(draftId, contractAddress)` via `eventBackfillDedupeKey` (NOT `draftId` alone — `notifyThread` fires at least twice per draft over its lifetime, once pre-mint and again at mint with `contractAddress` set, and a `draftId`-only key would let the pre-mint notice claim the slot and silently swallow the mint one). This is what lets a counterparty already live in the app see a first proposal without reloading from `/`.
5. **Opening a DM thread.** `useXaoDm({peer, session})` derives `dmThreadId(me, peer)` → `contentTopicForThread(...)`. `negotiateKey()`: check the conversation-key cache; if missing, `queryPeerKeyBundle(peer)`, then `deriveDmConversationKeyRaw`, cache it, `upsertConversation`, and best-effort publish a discovery `ThreadNotice{kind:'dm'}` to the peer's inbox (failure here doesn't block — the key is already usable locally). If no peer key bundle is found at all, status is `'no-peer-key'` and sends are blocked (peer has never used XaoMsg).
6. **Opening a draft's event thread.** `useXaoEvent({draftId, peer, session})` derives `threadIdForDraft(draftId)` → its own content topic, and negotiates the event conversation key the same way (cache-first, then `queryPeerKeyBundle` + `deriveEventConversationKeyRaw(..., draftId)`). `notifyThread(contractAddress?)` publishes a `ThreadNotice{kind:'event', draftId, contractAddress?}` to the peer's inbox and to the sender's own inbox (for cross-device continuity), fire-and-forget if no peer cert is cached yet.
7. **Thread pipeline (both kinds).** `useXaoThread` subscribes live *before* backfilling history (so nothing published mid-query is missed; `mergeResolved` dedupes overlap), decodes each byte payload → `decryptBody` → `JSON.parse` → `verifyEnvelope` (cert valid, not expired, sender matches cert, payload hash matches, signature valid) → `record()` → `onMessage` callback (fired once per unique `messageId`, guards against the sender's own light-push echo landing before/after the optimistic insert).
8. **Content-type routing.** `useXaoDm`'s `onMessage`: `CONTACT_CARD` → verify sender===peer and payload's own claimed address===sender, then `ProfileCache.setProfile()`; every other content type → `messagePreview.formatMessagePreview` → `conversationStore.upsertConversation` (a `null` preview, e.g. from a non-TEXT type, skips the conversation-list bump). `useXaoEvent`'s `onMessage`: every message → `draftSync.applyDraftMessage(resolved, myAddress, peer, proposalHashIndex, draftId)`, cross-checked against the thread's own `draftId` (see Off-chain contract drafts).
9. **Sending.** `useXaoThread.post()` builds the unsigned body, signs+hashes it into an `OnWireEnvelope`, AES-GCM-encrypts with the thread key, publishes to the topic, and does an optimistic local `record()` insert (deduped against the inevitable Waku echo of your own light-push).

## Data model / key types

`OnWireEnvelope = { body: MessageBody, payloadHash, signature, cert }`. `MessageBody = { v, messageId, threadId, contentType, parentHash, payload, sentAt, sender }`. Hashing goes through `hashableStringify` = `canonicalStringify(JSON.parse(JSON.stringify(value)))` — a real JSON round-trip *before* canonicalization, specifically so `undefined`-valued keys (routine in a partially-filled contract-proposal form) hash identically to what the wire actually carries after its own `JSON.stringify`/`JSON.parse` trip (see the long comment in `envelope.ts:5` — this was a real, previously-shipped bug: `8835072 fix(xaomsg): canonicalStringify must drop undefined-valued keys`).

`ContentType` (wire-locked integer values, do not reorder): `TEXT=0, PROPOSAL=1, COUNTER_PROPOSAL=2, ACCEPT=3, REJECT=4, SYSTEM=5, CONTACT_CARD=6`.

Thread ID derivation — three independent domains, none of which can collide with each other:
- `threadIdForShow(showAddress)` = `keccak256("xao-thread-v1" ‖ lower(address))` — the **legacy** one-thread-per-deployed-contract path (see Gotchas).
- `dmThreadId(a,b)` = `keccak256("xao-dm-thread-v1" ‖ sorted(lower(a), lower(b)))` — sorted so both parties derive the same ID regardless of who opens first. One per wallet pair, independent of any draft.
- `threadIdForDraft(draftId)` = `keccak256("xao-draft-thread-v1" ‖ draftId)` — one per contract draft, independent of the DM thread between the same two people and of any other draft's thread. Carries negotiation content pre-mint and keeps being used post-mint too (via the inbox mint-notice mapping — see Off-chain contract drafts).
- All three feed `contentTopicForThread(threadId)` = `/xao/1/<keccak256("xao-msg-topic-v1" ‖ threadId)>/json` — a *second* hash, so the Waku topic string doesn't reveal the thread ID (or contract address, or draftId) to an outside observer.
- `inboxTopicForAddress(addr)` = `/xao/1/<keccak256("xao-inbox-topic-v1" ‖ lower(addr))>/json` — deliberately *derivable from the address alone* (a cold sender needs to find it without prior contact).

`ThreadNotice = { kind: 'dm' | 'event', from, threadId, ts, preview?, draftId?, contractAddress? }` (`draftId`/`contractAddress` present iff `kind === 'event'`). Published ECIES-wrapped to the owning inbox, wallet-authenticated by the sender's `SessionCert`. `isValidThreadNotice` recomputes the expected `threadId` from `kind`+`from` (dm) or `kind`+`draftId` (event) and rejects any notice whose claimed `threadId` doesn't match — a wallet-attested sender can never mislabel which thread a notice is for.

## Off-chain contract drafts & contact cards

Contact cards ride the DM thread; contract negotiation content rides **its own per-draft event thread**, never the DM thread (`useXaoDm` deliberately has no draft-store access — see `5e80d70 refactor(xaomsg): stop useXaoDm from touching the off-chain contract store`). Both render in `XaoMsgComponent`'s `renderMessage()` as a muted, centered "system line" rather than a chat bubble (`ContactCardDisplay`-style copy, contract proposal/accept/reject/mint lines with emoji markers). `XaoMsgComponent` picks its mode from props: `draftId` set → event mode (`useXaoEvent`); `draftId` unset but `peer` set → DM mode (`useXaoDm`); neither → legacy `showContract` mode (`useXaoMsg`).

- **Contact card**: `useXaoDm` auto-sends one `CONTACT_CARD` envelope per thread the first time status flips to `'ready'` (guarded by `hasSentContactCard`/`markContactCardSent`, a `localStorage` set so a remount doesn't resend). Receiver applies it straight into `ProfileCacheContext.setProfile()`.
- **Off-chain draft lifecycle**: `create-contract.tsx` holds a stable per-negotiation `draftId` (`crypto.randomUUID()`, regenerated when the user points Party 2 at a new counterparty; reloaded from a stored/incoming proposal's own `draftId` so counter-proposals stay attached to the same draft) and opens a `useXaoEvent({draftId, peer, session})` for it. Compose → `PROPOSAL` (carries `Partial<IContract>` + `revisionNumber` + the `draftId`) → `offchainContracts.upsertDraft()` (strictly-higher `revisionNumber` always wins, so an out-of-order store replay can't regress a newer counter-proposal). Either party may `COUNTER_PROPOSAL` (same `draftId`, bumped revision). `ACCEPT` carries only a `proposalHash`; `draftSync` resolves it back to a `draftId` via a per-thread-replay `Map<bodyHash, draftId>` built as proposals are seen. Every PROPOSAL/COUNTER_PROPOSAL/ACCEPT/SYSTEM message is cross-checked against the thread's own `expectedDraftId` (the caller's hook params, never derived from the message itself) — a message that arrived on draft A's thread but claims to belong to draft B is dropped, so starting a throwaway draft with someone can never forge updates onto an unrelated draft of theirs.
- **Minting & mint continuity**: minting an on-chain `ShowContract` (an **existing on-chain flow**, see `contracts-nft` doc, completely untouched by XaoMsg) is followed by the minter posting a `SYSTEM {event:'minted', draftId, contractAddress}` on the draft's own thread, then calling `notifyThread(contractAddress)` to publish the mint pairing to both inboxes. The draft's event thread and key are reused unchanged after mint — there's no separate "post-mint" thread. `useResolveEventThread(contractAddress, onChainParty1, onChainParty2)` is what lets `contracts-detail.tsx` find that same thread later from just the minted address: it calls `resolveDraftForContract`, which requires a local draft to be **both** minted-to that exact address **and** have its own party1/party2 genuinely match the contract's real on-chain parties (either order, case-insensitive) before it's even a *candidate* — gating candidacy on both conditions together (not just preferring the address match and checking parties afterward) means a poisoned throwaway draft can never shadow and downgrade a real match just by being more recently active. No match → falls back to the legacy `threadIdForShow` path (`mode: 'legacy'`).
- **Fallback dedup** (`isMinted()`): if a draft has no recorded mint (e.g. minted on a device that never saw the SYSTEM message), it's hidden anyway once an on-chain summary matches `(party1, party2 in either order, eventName)` — heuristic, can mis-merge same-named contracts between the same parties.
- **Negotiation page** (`src/pages/contracts/Negotiation.tsx`) renders on-chain summaries (`useAllContractsWithSummaries`) plus not-yet-minted off-chain drafts (`useOffchainContracts`, which filters `listDrafts()` through `isMinted()`) as three visual buckets: "Requires Attention" (on-chain status 1/2), "Draft — off-chain", "Waiting" (on-chain status 0). **It does not itself talk to Waku** — it only re-reads `localStorage` when the connected wallet or on-chain summaries change; a draft only shows up here once *something else* (login sync, or `useXaoInbox` on the Search page) has already written it. A counterparty who never visits Search and never re-triggers `/unlock-chat` after a draft was sent to them will not see it here no matter how long they wait — see Gotchas.

## Integration points

- **`ProfileCacheContext`** (`src/contexts/ProfileCacheContext.tsx`) — generic `localStorage` profile cache (`xao-cult-profile-cache`), keyed by lowercased address, predates XaoMsg but is XaoMsg's only write path for peer profile data now.
- **Search page** (`src/pages/chat-Section/Search.tsx`) — the only mount point for `useXaoInbox`, so it's the only place live event-notice delivery and the one-time-per-mount inbox history replay happen outside of login sync. Its "Conversations" tab is 100% `useXaoInbox(session).conversations` (DM-only). Its "Events" tab merges on-chain contract summaries (`useGetUserNFTs`/`useAllContractsWithSummaries`, filtered to contracts the connected wallet is a party to) with not-yet-minted off-chain drafts (`useOffchainContracts`) into one list; clicking an off-chain draft loads its real terms via `sessionStorage` + `create-contract.tsx?peer=...`. "Start new conversation" accepts a raw `0x...` address typed into the search box (no separate contacts list).
- **Negotiation page** — see Off-chain contract drafts above; `contracts-nft` subsystem doc covers the actual minting call this page's `handleDraftClick` eventually leads to via `create-contract.tsx`.
- **`contracts-detail.tsx`** — resolves which thread to render for a minted contract via `useResolveEventThread` (draft mode) with a legacy fallback; see Off-chain contract drafts above.
- **`useGetContracts.ts` (`ContractSummary`/`useAllContractsWithSummaries`)** — the on-chain read side that `isMinted()`/`useOffchainContracts`/`useResolveEventThread` all merge against; not part of this subsystem.

## Gotchas & constraints

- **Spec drift — conversation-key transport.** The 2026-07-19 and 2026-07-24 spec docs describe the DM conversation key as *initiator-generated and ECIES-wrapped for transport*. That was replaced (commit `cb570d4 fix(xaomsg): derive DM conversation keys via ECDH instead of racing to transport one`) with the deterministic-ECDH-derivation scheme described above — no key is generated or transported at all anymore. Don't trust those specs' §4 on this point. The 2026-07-27 event-thread-separation spec is more current but is still a point-in-time design doc, not this doc — see its own "Follow-up" notes below for known deferred risk.
- **`src/lib/xaomsg/README.md` is stale.** It describes the pre-DM Phase-1 world (24h session, per-thread key from ShowContract address only, sessionStorage). Every one of those facts has changed. Update or delete it — this doc supersedes it.
- **Legacy contract-thread encryption was never upgraded.** `threadKey.ts`'s comment ("Plan 2 swaps in an ECIES handshake") never happened for the *contract-address-keyed* thread — `useXaoMsg`/`loadThreadKey` still calls `deriveDeterministicThreadKey(showAddress)`, a bare hash with no wallet-binding at all. Anyone who knows the deployed contract's address can derive that thread's AES key and read its chat. Only DM and event threads got the ECDH upgrade; a contract only reaches this legacy path when `useResolveEventThread` can't find a matching local draft (minted before this feature shipped, or on a device with no matching draft history).
- **Mint continuity does not survive a genuinely fresh device or a session-key rotation, not just Waku's store retention window.** Session keypairs are random per unlock, not derived deterministically from the wallet, and the mint-pairing notice is encrypted to one specific session's public key — so only that same session/device can ever decrypt it. A device that was live for the original mint notice, within its current 30-day session, gets real continuity; a fresh device, or the same device after its session has rotated, always falls back to the legacy path regardless of store retention. Closing this for real requires deterministic, wallet-signature-derived session keys, scoped as separate future work.
- **Peer key-bundle selection is by publish time, not self-declared expiry (fixed 2026-07-29).** `queryPeerKeyBundle` used to pick a peer's session cert by whichever valid, unexpired candidate had the furthest-future `expiresAtUnixMs`. A wallet that has ever created more than one session (a different device, a cleared `localStorage`, an earlier test run) can have several simultaneously-valid certs sitting in its inbox topic's history, and an abandoned one can easily have a *later* self-declared expiry than the session actually in use (expiry = creation time + 30 days — "created later" always sorts ahead of "created earlier" regardless of which one is still alive). This was a real, live bug: it silently encrypted notices to a session nobody held the private key for, so they never decrypted on arrival (a WebCrypto `OperationError`) — with zero error surfaced anywhere, permanently hiding a contract from its recipient. Fixed by ranking candidates by the Waku message's actual publish timestamp instead: a live session re-publishes its own unchanged cert on every `useXaoInbox` mount, so most-recently-published reliably tracks whichever session is actually current.
- **`notifyThread`'s `peerCertRef` isn't validated against the current peer (known, deferred, non-blocking).** `useXaoEvent.ts`'s `notifyThread` caches a resolved peer session cert in `peerCertRef` without re-checking it against the `peer` currently being negotiated for, or clearing it on a `peer`/`draftId` change mid-flight. If a user switches negotiations while a peer-cert lookup for the previous one is still in flight, a stale cert could theoretically be used to encrypt a notice intended for the new peer — the new peer's device fails to decrypt it (silent, no data exposure to them), while that notice's metadata (draftId, contractAddress, timing) leaks onto the *old*, unrelated peer's inbox topic. Confirmed pre-existing, not a third-party leak, does not affect `useResolveEventThread`'s draft-matching guarantees. Deferred per user decision (see `8aef8ea`); fix is small (pin `const targetPeer = peer` at the start of the lookup and validate `cert.walletAddress` against it before using/caching) but not yet done.
- **In-component "24h" copy is stale and misleading.** `XaoMsgComponent.tsx` (the fallback in-chat unlock button, used only if a session expires mid-session) still says "XaoMsg unlocks for 24 hours" / "Unlock chat for 24h" — the actual duration is 30 days. Cosmetic but user-facing; fix opportunistically if touching that file.
- **Waku light-push peer count.** Default is 1 peer; if that peer requires an RLN anti-spam proof (which this client never generates), every send fails outright. Fixed by requesting 3 peers (`waku.ts`, commit `916fd8b`) so one RLN-requiring peer isn't a single point of failure. A partial per-peer failure (some succeed, some don't) is treated as success; only *total* failure throws.
- **`conversationKey` storage key is versioned (`-v2`).** A prior scheme (pre-ECDH, each side could independently generate a key with no negotiation, permanently diverging the two views of a thread) is intentionally orphaned rather than migrated — old `-v1` entries are simply ignored, forcing a fresh ECDH derivation.
- **`useXaoMsgSession.ts` comment says "Restore from sessionStorage"** but the actual backing store is `localStorage` (per the 30-day change) — comment lagged the code, harmless but can mislead a reader.
- **StrictMode / concurrent-negotiation guard.** Both `useXaoDm.ts` and `useXaoEvent.ts` keep a module-level `inFlightNegotiations: Map<Hex, Promise>` specifically to dedupe React StrictMode's dev-mode mount→cleanup→mount (or any fast remount) so two effect instances never both fire a peer-key lookup + discovery-notice publish for the same thread concurrently.
- **`useOffchainContracts` infinite-loop fix.** `useAllContractsWithSummaries`'s `contracts` array is a new reference every render even when on-chain data hasn't changed; depending on it directly caused "Maximum update depth exceeded" (observed live). Fixed by deriving a stable string key (`summariesKey()`) from the array's content and depending on that primitive instead.
- **Inbox topic is a metadata side-channel.** Anyone who knows your address can compute `inboxTopicForAddress(you)` and observe *that* you receive DMs/event notices and their timing/volume (notices are ECIES-encrypted, so not sender/content/draftId). Publishing a key bundle also reveals you use XaoMsg at all. No spam control on cold notices — anyone can post to your inbox topic; only signature/cert checks gate what's *trusted*, not what's *accepted onto the topic*.
- **Waku store peers are best-effort.** `queryHistory` waits up to 15s for a Store protocol peer and silently returns (logs a warning) if none connects — some bootstrap nodes don't serve Store. History backfill can silently be a no-op; this is not surfaced to the UI.
- **Negotiation page is a passive reader, not a Waku subscriber.** As noted above, it never itself triggers a fetch — a draft only appears there after login sync or a Search-page visit has already populated `localStorage`. If you're debugging "a sent contract never showed up," check whether the recipient has visited Search (or freshly unlocked) since it was sent before suspecting the transport layer.
